# Round-2 review — Settings, backup/restore, theme & language

**Branch:** `feature/review-round-2` @ `fbc8e15` (= main, release 0.0.61). Read-only; no product/test/docs code changed.
**Scope:** `ui/settings/**` (screen, sections, rows, `SettingsViewModel`, `RestoreCompletion`), `data/backup/**`, `RepositorySettings.kt`/`GradingRulesStore.kt`, `ui/theme/**`, `McqApplication.kt` (`AppLocale`), `MainActivity.attachBaseContext`, storage measurement, resets, export/restore errors.
**Method:** old `review-reports/07-settings.md` treated as **claims**; `git log 0.0.53..HEAD` + full diffs read for all six settings-touching commits. Platform claims checked against official docs, cited inline.

## Verdict

Most old High/Medium claims (restore busy wedge, "Measuring…", raw VM error copy, backup atomicity) are genuinely fixed. The new language picker is sound in isolation and avoids double recreation. But hoisting operation *execution* to the ViewModel while leaving its *result/busy state* in `rememberSaveable` composable state creates a High bug: any Activity recreation mid-operation orphans the callbacks and wedges every Backup & data control. Two Hindi-parity gaps and one raw-exception leak also remain.

## Findings

**SE1 — High — A language change (or rotation) mid-export/backup/restore/share leaves the new composition busy forever and shows no result.** `SettingsScreen.kt:82-87` keeps `busy`, `exportError`, `exportErrorTitleRes`, `restoreDone` in `rememberSaveable`; `:145-148` (`fail`), `:155`, `:163`, `:331-336` pass closures that write those setters into the ViewModel; `RestoreCompletion.kt:33-46` invokes them at the end. The ViewModel survives configuration change and its coroutine keeps running ([ViewModel overview](https://developer.android.com/topic/libraries/architecture/viewmodel): "asynchronous work continues in the ViewModel" across config changes; "When the host activity undergoes a configuration change"), while `Activity.recreate()` builds a *new* composition with *new* state objects restored to `busy=true`. `setApplicationLocales` recreates the Activity ([LocaleManager](https://developer.android.com/reference/android/app/LocaleManager#setApplicationLocales(android.os.LocaleList)): "configuration change (and potentially an Activity lifecycle event)"; [app-languages](https://developer.android.com/guide/topics/resources/app-languages#framework-impl): "system automatically updates the locale and restarts the app"), and a restore whose backup carries a different language triggers exactly this path near the end of `settingsRestore` (`McqRepository.kt:619-641`). `onComplete()` clears the orphaned state; the live `busy` stays true, so all buttons in `BackupDataSection.kt:57-112` remain disabled with no success/error dialog. Rotation mid-restore has the same effect. *Why missed:* the H4 fix added `onComplete` but kept the state owner in the composable; `RestoreCompletionTest` tests the seam, not ownership across recreation. *Fix:* move `busy`, error title/message and restore report into `SettingsViewModel` (`StateFlow`/one-shot event), or bind callbacks to a saved-state-backed owner that outlives the Activity.

**SE2 — Medium — Log-export failure copy and chooser title stay English under Hindi.** `BackupDataSection.kt:119` (`"No log file exists yet."`), `:135` (`createChooser(intent, "Export Logs")`), `:138` (`"No app can handle this share."`) are literals shown in the error dialog/window. `R.string.export_logs` exists in both locales (`values/strings.xml:174`, `values-hi/strings_hi_1.xml:183`), so the chooser title is a one-line fix; the two messages need new resources in both. *Why missed:* the 0.0.57/0.0.59 `final_*` copy sweep covered ViewModel literals; resource-usage tests cannot flag plain `Text`/`String` literals. *Fix:* resource ids + `stringResource`/`resources.getString`.

**SE3 — Medium — Restore's success/partial report is untranslated and leaks raw exception text.** `Backup.kt:1242,1248` append `e.message` into `partial[]`; `:1258-1264` build an English sentence, shown verbatim at `SettingsScreen.kt:351` (`Text(report)`). The non-streaming twin does the same at `:1083,1089,1103-1110`. A partial settings restore therefore puts e.g. `settings were not restored (java.io.IOException: …)` on screen, contrary to PROJECT_NOTES §Localisation ("raw exception detail goes to Logger only"). Hindi users see the entire report in English. *Why missed:* the error-path localization touched only `handleRestoreCompletion`; the data-layer report string was left as a human sentence. *Fix:* return counts/flags + a localized renderer (resId+args) from `BackupRestorer`; log `e.message`, show a resource-backed generic partial note.

**SE4 — Low — Removing the selected custom theme can still leave a dangling palette key.** `SettingsViewModel.kt:239-255` decides the fallback by comparing `_themePalette.value` (a StateFlow that a DataStore collector updates asynchronously, `:99-102`) with the removed key. If removal lands before the collector publishes the imported key, the check is false and the stored palette keeps pointing at a deleted theme. It does not crash — `Theme.kt:17-19` / `AppThemes.kt:271-272` fall back to Material — but the picker shows Material with no checkmark. Old audit's Low item is unchanged. *Fix:* read the palette under the same DataStore edit/after it, or clear the key whenever it names the removed theme regardless of the cached snapshot.

**SE5 — Low — `share()` has no one-shot guard.** `SettingsScreen.kt:121-143` sets `busy=true` synchronously but launches a coroutine; a second tap before recomposition can start two `build()` calls and hand two chooser intents to the system. The old "stuck busy on cancellation" half is *not* reproducible (`shareAllIntent`/`shareBackupIntent` catch `Exception`, `SettingsViewModel.kt:844-847,924-927`, so `busy=false` still runs) — the stuck part is SE1. *Fix:* return early when `busy`, or own the flag in the VM (SE1).

**SE6 — Low — Pre-33 startup does a blocking DataStore read on the main thread, and the rare locale sync runs off-main.** `AppLocale.storedLanguage()` uses `runBlocking` (`McqApplication.kt:165-173`) inside `MainActivity.kt:30-35` `attachBaseContext`, so every cold start/rotation blocks for a disk read; the official guide warns that custom-storage locale pickup "causes a blocking read on the main thread and might cause a StrictMode diskRead and diskWrite violation" ([app-languages](https://developer.android.com/guide/topics/resources/app-languages#support-android-12-and-lower)). `McqApplication.kt:144-150` calls `applyPlatform` from `startupScope` (`Dispatchers.IO`); the equality guard at `:212` makes it a no-op on a normal cold start, so only a mismatch path writes from a background thread, where AndroidX guidance says to call `setApplicationLocales` on the main thread. *Fix:* cache the choice in a main-thread-safe holder / `SharedPreferences` for attach, and dispatch the sync to Main.

## Re-verified as fixed since 0.0.53

- **H4 (failed restore wedges busy):** `RestoreCompletion.kt:44-46` `finally { onComplete() }`; `SettingsScreen.kt:335` passes it; `RestoreCompletionTest.kt:66-105` covers success/too-large/generic and raw-detail suppression. (Ownership gap is SE1.)
- **"Measuring…" forever:** `StorageLoad.kt:14-33` sets an error on failure and clears a stale report; `SettingsViewModel.kt:625-652`; `BackupDataSection.kt:162-173` renders error + Retry; announced at `SettingsScreen.kt:108-110`.
- **Raw/technical VM copy:** `SettingsViewModel.kt:68-78` resolves every message via `msg()`/`pluralMsg()`; 42 `final_*` names exist in both English and Hindi; `BACKUP_RULE_MOVED` is now a token (`:806,1013`) mapped at `:814-818`.
- **Per-keystroke unrelated-edit version minting:** `SettingsViewModel.kt:457-515` edits stored config under a mutex; `setAppLanguage` no-ops identical taps (`:145-150`).
- **Restore atomicity:** `Backup.kt:1159-1220` wipes and replays inside one `db.withTransaction`; settings/in-progress failures are caught (`:1238-1249`) and the FSRS rebuild is process-scoped (`McqRepository.kt:619-641`).
- **Theme import cap/size guard:** `SettingsViewModel.kt:158-205`, `CustomTheme.kt:53-59,144-197`.

## Checked, no defect

- **No double recreate on 33+:** collector guards `needsExplicitLanguageRecreate()` (`SettingsViewModel.kt:137-140`, `McqApplication.kt:37-39`); manifest has no `configChanges`; first-emission skip (`:130-136`) prevents a loop on re-entry/restore.
- **Locale reaches Compose:** `MainActivity.kt:34` wraps the Activity context pre-33; on 33+ the platform applies app locales before Activity creation ([app-languages](https://developer.android.com/guide/topics/resources/app-languages#compose-impl)); VM copy uses `AppLocale.localized` (`:68-78`).
- **Language resource parity:** `LanguagePickerResourcesTest` + 42/42 `final_*` names; `AppLanguage.fromStored` falls back to SYSTEM on corrupt values.
- **Reset flows/error display:** `SettingsViewModel.kt:527-539` no longer publishes a false `SchedulerConfig()`; `resetError` is resource-backed.
- **Storage cap/preview:** `SettingsSections.kt:12,44-52`; KiB/MiB mislabelled as KB/MB (`StorageInfo.kt:31-36`) is a cosmetic nit, not a defect.
- **SAF URI:** `restoreUri` is saveable (`SettingsScreen.kt:168`); the grant survives configuration change within the task.
